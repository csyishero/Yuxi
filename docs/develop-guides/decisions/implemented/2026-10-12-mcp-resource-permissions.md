# MCP 服务级权限

状态：implemented
类型：feature
Owner：backend/package/yuxi/permissions/resource_permission.py

## 问题

管理员启用的 MCP 服务原本会进入所有用户的智能体候选资源和运行时工具集合。页面隐藏不能阻止已保存的 Agent 配置、Skill 依赖或长时间运行的工具调用继续使用服务。

## 决策

每个 MCP 使用现有 `read_scope`、`edit_scope`、`manage_scope` 权限树。查看权允许读取脱敏元数据；使用权允许选择并调用工具；管理权允许修改该服务的共享范围。管理范围只授予指定用户。系统管理员单独拥有连接配置、密钥、全局启停、工具启停和连接测试权限。被委派的普通管理者只能向本部门或本部门用户授权，候选人接口只返回本部门成员。

历史 MCP 的 `share_config` 为 NULL 时，所有已登录用户保持查看和使用权，系统管理员逐个收紧；启动流程已停用的历史用户 `stdio` 服务仍不可使用。新建 MCP 使用私有共享配置，仅系统管理员默认可见和可用。服务全局禁用或单个工具禁用会阻止调用。普通用户的 MCP 响应只包含基础信息；Agent 与 Skill 的结构化配置响应按当前用户可见性投影 MCP 引用，保存投影后的配置保留不可见的旧引用。Skill 原文的正文仍可能由作者自行写入服务名称，不能将正文内容当作权限证明。

Agent 和 Skill 在运行准备时按当前用户使用权筛选 MCP；每次实际工具调用前重新读取用户、服务和工具状态并复核权限。连接地址和凭据变更在新 Run 重新装配工具时生效。权限解析、MCP 服务用例、Agent/Skill 资源规范化、工具执行守卫和 HTTP 路由分别拥有这些运行事实。

## 替代方案

- 只在 MCP 页面隐藏服务：已保存的引用和直接接口调用仍可使用工具。
- 为每个 MCP 工具单独建立权限树：粒度更细，但当前授权对象是服务，会增加配置和执行成本。
- 新建用户与服务授权表：查询关系明确，但会与现有共享范围并行维护两套授权模型。

## 后果

已启用的历史服务继续对全体登录用户可用，直至系统管理员逐个收紧。被委派管理者只能调整本部门的授权；既有全员或其他部门授权保持原样，由系统管理员负责调整。已开始的运行不会自动中断；撤权或停用后，下一次 MCP 工具调用会被拒绝。活动 Run 已挂载的共享 Skill 文件可能保留撤权前可见的名称，下一轮运行重新生成投影。外部服务仍使用管理员配置的共享连接凭据，不自动取得 Yuxi 用户身份。

## 验证

- 权限与路由单元测试覆盖历史与新建默认值、部门边界、私有服务 404、脱敏响应和无权工具调用。
- 真实 PostgreSQL 迁移与 HTTP 测试覆盖 Schema v9、旧数据兼容、共享授权及配置引用可见性。
- MCP 工具调用守卫测试覆盖运行中撤权、服务停用、工具停用和共享缓存隔离；Agent/Skill 测试覆盖资源筛选和不可见旧引用保留。
- 前端 lint、unit、build、真实页面检查和文档构建验证权限展示与编辑流程。
