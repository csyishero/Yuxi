# 个人 Skill 申请共享

状态：implemented
类型：feature
Owner：backend/package/yuxi/agents/skills/sharing.py

## 问题

个人 Skill 只存在用户工作区，管理员可以直接安装共享 Skill，但个人成果无法从现有页面申请进入共享库。上传一个新副本会丢失来源、审核状态和发布范围的联系。

## 决策

用户对自己的个人 Skill 提交共享申请。提交时在平台持久目录保存快照和内容摘要，申请记录保存在 PostgreSQL；同一 Skill 同时只允许一条待审申请。快照最多 1000 项、20 MB；复制时通过目录 fd 逐项禁止跟随符号链接，复制和哈希在线程中运行。申请人能看状态，管理员能检查完整目录与文本内容、下载原始快照、驳回或选择指定部门或人员发布。管理员也可按[部门个人 Skill 查询与管理员直接发布](./2026-10-10-department-personal-skill-publishing.md)直接从授权成员的当前个人原件创建快照并发布。发布生成独立的共享 Skill，个人原件始终保留。共享 slug 已占用时发布为递增后缀的新 slug，且最终长度不超过数据库字段限制，不替换现有 Skill。审批记录保存发布 slug、审核人、时间、意见、读取范围和快照摘要；已发布副本的内容与依赖不可原地编辑，个人 Skill 修改须重新申请。

读取范围支持指定部门或指定人员，发布后可在两者之间调整；不允许全局读取或额外分配管理权限。共享者不可自行选择发布范围。部门管理员只看和审核本部门申请，只能发布到本部门或本部门有效人员；超级管理员可跨部门选择。共享 Skill 的创建者记为审核管理员，申请人不会获得共享副本的管理权。个人 Skill 与共享 Skill 同名时继续按现有优先级使用个人版本，界面明确提示覆盖关系。依赖按现有共享 Skill 规则在审批时验证。读取范围扩展的详细决策见[个人 Skill 共享副本支持指定部门或人员](./2026-10-10-personal-skill-share-audience.md)。

## 替代方案

直接把个人 Skill 移入共享目录实现较短，但会破坏个人工作区和后续迭代。复用一小时 TTL 的安装草稿不能承受管理员异步审批。只加管理员上传入口没有申请与追踪。原位更新同名共享 Skill 会意外改变现有用户行为。

## 后果

未分配部门的用户也可提交共享申请，仅超级管理员可审核；无部门的部门管理员不能查看或审核。

新增申请表和快照目录；申请表作为兼容业务 Schema 8 的增量结构，由每次启动前的迁移器幂等建表，现有部署不需要升级业务版本号。发布时文件与数据库分处两个事务边界，数据库失败时回滚文件；服务在文件重命名后、数据库提交前崩溃仍可能留下孤立目录，沿用现有共享 Skill 安装的运维清理方式。服务重启后待审记录仍可继续处理。发布版本用新的 slug 保持可追溯，完整版本树和差异审批不在当前机制内。

## 验证

Skill sharing unit 5 项通过，覆盖快照不随原件修改、文件树、脚本、压缩包、目录大小、发布权限、长 slug、并发符号链接和复制时文件增长。隔离 PostgreSQL 下真实 HTTP 与旧库 Schema 迁移通过，覆盖跨部门拒绝、普通用户审核拒绝、文件路径越界、完整快照发布、发布后编辑限制及迁移重放。Web lint 和生产构建通过；使用模拟数据在本地页面查看了申请列表、完整快照、脚本内容与返回流程。全量回归中的历史测试失败与受限环境另行记录在交付说明。
