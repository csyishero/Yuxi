# 部门个人 Skill 查询与管理员直接发布

状态：implemented
类型：feature
Owner：backend/package/yuxi/agents/skills/sharing.py

## 问题

部门管理员需要按人员查找和预览本部门的个人 Skill，并能把适合团队复用的成员 Skill 发布到部门共享库。超级管理员跨部门管理个人 Skill，普通成员只管理自己的个人原件。

## 决策

个人 Skill 目录按管理员权限查询：部门管理员只看所属部门有效成员，超级管理员可筛选所有部门。跨用户文件预览和直接发布都在后端重新核对所有者身份、有效状态和所属部门，URL 中的 uid 不产生授权。管理员从个人 Skill 预览中选择[目标部门或人员](./2026-10-10-personal-skill-share-audience.md)并确认发布；部门管理员只能选择本部门或本部门有效人员，超级管理员可跨部门选择。

直接发布为当前个人原件创建不可变快照，再复用共享审核发布链路生成独立共享副本。个人原件始终保留。发布记录保存原件所有者、快照摘要、审核管理员、目标部门和共享 slug；审核意见标明“管理员直接发布”。已有待审申请时拒绝直接发布，避免误用申请时的旧快照。发布校验失败时移除本次产生的待审记录和快照。跨用户个人原件的编辑与删除仍由所有者操作；管理员对成员 Skill 的管理入口是查询、预览、审核和直接发布。

目录权限由 `skills/service.py` 拥有；路由在 `skill_router.py` 进行身份和请求适配；`SkillCardList.vue` 提供部门查询、预览和发布交互。发布不新增数据库 schema 版本。

## 替代方案

- 只扩展目录可见性，继续要求所有者提交申请：管理员无法主动发布已核验的个人 Skill。
- 直接移动或改写所有者个人目录：破坏原件和个人运行行为，也失去审核快照。
- 绕过申请表直接上传共享副本：无法沿用现有来源、快照和发布审计。

## 后果

管理员可以主动把本部门成员内容复制到共享库；管理员自己的个人 Skill 也使用“直接转为共享”，普通成员使用“申请共享”。页面在最终确认前展示所有者、Skill 与目标受众。已有申请必须走原审核流程。文件与数据库发布仍处于现有双存储边界，沿用发布失败回滚文件的处理；进程在文件重命名后、数据库提交前崩溃仍可能留下孤立共享目录。

## 验证

- 个人 Skill 目录 HTTP 集成测试通过：普通用户拒绝、部门管理员按人员查询与跨部门拒绝、超级管理员跨部门筛选和有效用户预览。
- 隔离 PostgreSQL schema 的 HTTP 集成测试通过：普通用户与跨部门管理员拒绝，非法目标部门回滚，合法发布保留原件并回读共享行、快照和操作者；已有待审申请拒绝直接发布。
- 前端相关 ESLint 与 Vite 生产构建通过；本机 Yuxi API readiness 为 200，管理员目录显示按部门和人员查询，个人 Skill 预览显示“直接转为共享”及目标部门确认界面。
- 工程契约检查仍有 4 项既有文档元数据错误，均在其他决策文件中；本记录与功能代码未触及这些文件。
