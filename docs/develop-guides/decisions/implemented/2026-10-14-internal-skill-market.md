# 内部 Skill 市场

状态：implemented
类型：feature
Owner：backend/package/yuxi/agents/skills/market.py

## 问题

现有共享 Skill 按授权范围自动进入用户的可用集合。员工无法从一个按场景组织的目录中发现、主动安装和评价同事发布的 Skill；共享申请也没有稳定的市场条目与版本关系。

## 决策

员工从个人 Skill 提交不可变审核快照，并固化提交时的所属部门。部门管理员可发布到该部门，超级管理员可发布到全公司。市场条目保留稳定 slug，审核通过后产生不可变版本；员工在统一技能页的“市场”分类搜索可见条目，在分类内的排行榜查看安装或点赞情况，并查看作者、范围、依赖及发布文件。审核员可下载包含附件的完整快照。员工主动安装，升级时再手动确认；Agent 只接收本人已安装的市场 Skill，运行时解析固定版本的文件目录。现有内置和共享 Skill 仍自动可用，两个发布渠道的待审申请分别去重，发布标识互相避让。

统一入口、榜单的公司及部门范围、超级管理员跨部门可见性由 [技能目录的展示层级与部门范围](2026-10-15-skill-hub-discovery-controls.md) 补充；本记录保留市场发布、安装和版本的决定。

PostgreSQL 拥有条目、版本、安装指针、点赞和审核状态；文件系统保存审核快照与已发布版本。市场服务负责审核与安装事务，市场 repository 负责可见性和排行查询，运行时负责将稳定 slug 对应到固定版本目录。安装人数按当前安装用户数计算，点赞按用户去重；排行榜只查询当前用户可见条目。首版市场 Skill 可依赖现有非市场 Skill，不支持市场条目之间的依赖。

## 替代方案

- 直接给现有共享 Skill 卡片加热度：实现较快，但无法表达主动安装、版本与审核发布边界。
- 为每个安装创建个人 Skill 副本：会导致更新分叉和大量重复文件，不利于撤销授权。
- 引入外部 Skill 仓库服务：首版没有跨实例分发需求，增加额外信任边界。

## 后果

新版本发布不会自动改变已有安装。旧运行的版本文件继续保留；文件发布与数据库提交之间若结果不确定，优先保留可能成为孤儿的版本目录，避免删除已提交版本。市场授权收紧时，未开始的运行不再获得该 Skill。首版未提供卸载、分类筛选或累计下载次数；界面显示的是当前安装人数。旧共享条目不会自动迁移进市场。

## 验证

真实 PostgreSQL 与 HTTP 集成测试覆盖审核范围、普通成员和部门管理员跨部门不可见、超级管理员跨部门可见、安装与点赞、手动升级后的固定版本目录、市场与共享并行申请及同名发布避让；Schema 从 v10 的幂等升级测试覆盖待审索引和新表。相关运行时与动态激活单测、前端 lint、构建通过。完整后端单测包含 `test` 分支原有的 Compose/知识库测试失败和本机沙盒限制；浏览器页面截图及真实 Agent Run 尚未验证。
