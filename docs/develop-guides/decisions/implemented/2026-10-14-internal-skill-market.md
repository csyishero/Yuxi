# 内部 Skill 市场

状态：implemented
类型：feature
Owner：backend/package/yuxi/agents/skills/market.py

## 问题

现有共享 Skill 按授权范围自动进入用户的可用集合。员工需要从按场景组织的目录中发现、主动安装和评价同事发布的 Skill，并明确区分共享发布与市场上架的使用规则。个人 Skill 分别从管理入口申请共享、从目录入口申请上架时，作者难以在同一处核对两条发布记录。

## 决策

员工从个人 Skill 提交不可变审核快照，并固化提交时的所属部门。部门管理员可发布到该部门，超级管理员可发布到全公司。市场条目保留稳定 slug，审核通过后产生不可变版本；员工在统一技能目录按来源、方向和关键词搜索可见条目，从“市场热门榜”查看安装或点赞情况，并查看作者、范围、依赖及发布文件。审核员可下载包含附件的完整快照。员工主动安装，升级时再手动确认；Agent 只接收本人已安装的市场 Skill，运行时解析固定版本的文件目录。现有内置和共享 Skill 仍自动可用，两个发布渠道的待审申请分别去重，发布标识互相避让。

个人 Skill 的“发布技能”是作者统一入口：先选“直接共享”或“上架市场”，再共用技能方向、发布说明和当前文件预览。提交后同一窗口分别显示两条渠道的最近申请状态、发布范围、版本与不可变提交快照；新发布的共享申请还按发布时保存的副本 ID 查询当前状态，明确标注已启用、已停用或已删除。旧申请没有可靠副本 ID，状态标注为未确认，不能靠同名记录推断。普通用户选择直接共享时提交共享审核，批准后按共享授权自动可用；选择上架市场时提交市场审核，批准后成员仍须主动安装。管理员只能对**自己的**个人 Skill 直接发布共享副本，可继续审核别人主动提交的申请。共享审批与市场审批保留独立的范围、版本及安装语义，不合并持久申请、市场条目或安装指针。

统一入口由 `web/src/components/extensions/PersonalSkillPublish.vue` 组织；共享申请和直接共享由 `backend/package/yuxi/agents/skills/sharing.py` 处理，市场审核、版本与安装由本记录 Owner `market.py` 处理。两个渠道的申请状态仍在 PostgreSQL 中分别记录；按本人读取申请记录不依赖管理员当前审核部门范围，管理员的审核列表继续按原有部门权限过滤。

同一作者的同一个人 Skill 再次提交市场审核时，沿用已有市场条目的发布范围及部门。申请列表从现存市场条目返回这两个字段；审核弹窗预选并固定原范围，并说明原因。API 审核省略范围时沿用已有条目范围，首次发布默认申请人部门；显式传入不同范围仍被拒绝。部门管理员无法批准已有全公司条目或作者已调离原发布部门的新版；跨部门续版由超级管理员审核，发布后仍面向原部门。后端继续校验范围及部门，防止绕过页面或并发修改导致越权发布。

个人空间的收展、榜单的公司及部门范围、超级管理员跨部门可见性由 [技能目录的展示层级与部门范围](2026-10-15-skill-hub-discovery-controls.md) 补充；本记录保留个人 Skill 的发布入口以及市场发布、安装和版本的决定。

PostgreSQL 拥有条目、版本、安装指针、点赞和审核状态；文件系统保存审核快照与已发布版本。市场服务负责审核与安装事务，市场 repository 负责可见性和排行查询，运行时负责将稳定 slug 对应到固定版本目录。安装人数按当前安装用户数计算，点赞按用户去重；排行榜只查询当前用户可见条目。首版市场 Skill 可依赖现有非市场 Skill，不支持市场条目之间的依赖。

## 替代方案

- 直接给现有共享 Skill 卡片加热度：实现较快，但无法表达主动安装、版本与审核发布边界。
- 为每个安装创建个人 Skill 副本：会导致更新分叉和大量重复文件，不利于撤销授权。
- 引入外部 Skill 仓库服务：首版没有跨实例分发需求，增加额外信任边界。
- 保留共享申请和市场上架两个分散入口：不改变服务端模型，但作者难以一起查看发布状态、范围和版本。
- 把共享与市场合为一种发布记录：会掩盖共享自动可用、市场主动安装及市场安装版本固定的差异。
- 允许管理员直接发布他人的个人 Skill：绕过作者提交意愿及其审核快照，故仅保留对本人个人 Skill 的直接共享。

## 后果

新版本发布不会自动改变已有安装。旧运行的版本文件继续保留；文件发布与数据库提交之间若结果不确定，优先保留可能成为孤儿的版本目录，避免删除已提交版本。市场授权收紧时，未开始的运行不再获得该 Skill。员工可以按方向筛选、卸载本人安装；界面显示当前安装人数，不记录累计下载事件。旧共享条目不会自动迁移进市场。

发布入口整合不合并发布表，也不改写历史共享副本、市场版本及安装记录；只给共享申请增加可空的发布副本 ID，用于核验新申请的当前状态。旧申请留空且显示状态未确认，不从 slug 猜测副本。已有安装版本仍由用户主动升级，原有 Agent 选用的 slug 和个人原件继续按现有优先级解析。两条渠道可各有一笔待审申请；已发布内容不会因作者改动原件而变化。业务 Schema 从 v13 升到 v14 时只补这一个可空列，并记录版本，不重跑旧归属回填。内网已有数据库升级时由现有 `storage-migrator` 在业务服务启动前执行，按[部署指南](../../../advanced/deployment.md)完成停机备份、迁移和启动，不手写 SQL。

## 验证

真实 PostgreSQL 与 HTTP 集成测试覆盖审核范围、普通成员和部门管理员跨部门不可见、超级管理员跨部门可见、安装与点赞、手动升级后的固定版本目录、市场与共享并行申请及同名发布避让；Schema 的幂等升级测试覆盖待审索引、新表以及旧库增加可空发布副本 ID。测试还覆盖首次申请没有既有范围、已有部门条目新版沿用原部门、作者调部门后由超级管理员续版、已有全公司条目错误范围被拒绝后按原范围发布、管理员不能直接发布他人个人 Skill，以及本人申请记录独立于审核部门范围。共享历史测试覆盖副本删除后同名重建仍显示原副本失效，旧记录状态未知。前端审核交互测试覆盖范围锁定提示，统一发布窗口测试覆盖作者权限、两个渠道的状态与提交。相关运行时与动态激活单测、前端 lint、构建通过。完整后端单测包含 `test` 分支原有的 Compose/知识库测试失败和本机沙盒限制；浏览器页面截图及真实 Agent Run 尚未验证。
