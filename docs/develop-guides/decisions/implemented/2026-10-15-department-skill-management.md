# 部门管理员管理本部门共享 Skill

状态：implemented
类型：feature
Owner：backend/package/yuxi/permissions/resource_permission.py

## 问题

审核发布的共享 Skill 以审核员作为 `created_by`，默认不设置 `manage_scope`。同部门的另一位管理员虽然可以查看和使用，仍只能以只读方式打开配置页，无法接管本部门的 Skill。把“可见”直接当作“可管理”又会让部门管理员接管全公司或跨部门发布的 Skill。

## 决策

部门管理员仅对归属本部门、且读取范围明确只包含本部门的共享 Skill 继承管理权限。审核发布副本的归属取申请提交时的部门快照；直接上传或远程安装的共享 Skill 在创建时记录归属。无法可靠确认归属的旧记录保持原有显式授权。部门为空、全局、跨部门及指定人员的读取范围不产生这项隐式授权。内置 Skill 的现有管理员规则、个人原件的本人管理规则和市场发布条目保持原有权限。已审核发布的共享副本仍不得直接修改内容和依赖。

管理动作沿用现有 Skill API 和 `can_manage` 响应。仅靠部门继承管理权的管理员可以启停、导出、删除；未审核的共享上传或远程 Skill 仍可按现有规则编辑文件与依赖，已审核副本保持只读。继承权限不允许修改 `share_config` 或自行添加显式管理授权，防止先自委派再扩大到其他部门或全公司。失去所属部门后立即失去这项权限。前端按服务端权限开放入口，并说明当前管理范围。

## 替代方案

- 让任何能查看 Skill 的部门管理员都可管理：会把全局和跨部门发布误交给一个部门。
- 仅按当前单部门读取范围推断归属：会把其他部门提交、由超级管理员定向发布的 Skill 错误交给受众部门管理。
- 每次审核都额外写入部门管理员名单：人员变化后需要同步授权，不能自然体现现任部门管理员职责。

## 后果

归属信息由服务端写入共享 Skill 的权限元数据，客户端不能借保存共享范围改变它。业务 Schema 从 12 升至 13；旧审核发布副本以唯一匹配的已批准申请回填，无法可靠确认来源的历史记录不自动授予管理权。发布给指定人员的 Skill 即使所有人都在本部门，也不会自动获得部门管理员权限。

## 验证

- 相关权限和服务单测 60 项通过；真实 HTTP/PostgreSQL 集成测试 4 项通过，覆盖本部门管理员管理、他部门发布物拒绝、连续自委派和扩大全公司的请求均拒绝、数据库共享配置不变。
- 真实 PostgreSQL 的 v12→v13 `storage_migration.main()` 测试通过，覆盖版本写入、可信申请回填和重复运行幂等。
- Ruff、格式检查和 `git diff --check` 通过。整份相关集成文件另有两个未修改的旧用例失败：旧请求缺少必填方向；MCP 测试地址包含 `secret` 干扰旧断言。本次目标用例均通过。
