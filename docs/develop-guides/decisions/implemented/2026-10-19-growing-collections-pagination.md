# 增长型列表按需读取

状态：implemented
类型：feature
Owner：backend/package/yuxi/repositories/conversation_repository.py

## 问题

API Key、后台任务、文件搜索和授权选人在固定条数后遗漏结果。会话历史、技能发布记录、评估概览、管理员反馈和技能目录随数据增长增加数据库、网络与页面负担。接口具备分页能力时，页面仍须提供用户取得下一批数据的入口。

## 决策

增长型数据库集合由各领域的 repository 按稳定顺序和原有权限条件分页查询。对应 `web/src` 页面用页码或“加载更多”发起下一批请求；单项详情按标识读取。文件搜索由 workspace 文件访问层按扫描预算继续取得结果，明确提示截断，并支持在预算之外按授权路径精确查找。会话历史默认保持旧接口的完整读取语义；聊天页面显式请求最新一批，再按游标取得更早消息和运行记录。

技能目录按来源分别读取个人、共享与市场安装记录；Agent 运行时继续读取完整可用技能集合。旧客户端不传分页参数时，保留相关列表的原有返回语义。个人技能目录的旧接口即使显式传入 `limit`，仍按人员翻页；新版页面传 `card_page=true`，按技能卡片翻页。权限始终由后端的可见性查询和单项授权决定。这项决定不改变既有记录、安装数据或数据库结构。

## 替代方案

- 仅在浏览器内切分已返回的数组：同屏元素减少，数据库与网络仍传送完整集合。
- 提高固定条数上限：只能推迟遗漏数据，响应大小继续随数据量增长。
- 建立跨所有资源的统一分页框架：这些资源的顺序、权限和存储方式不同，统一抽象增加维护面。

## 后果

列表查询需要稳定排序及与权限一致的计数；删除或状态变化会使当前页缩短，页面须回退或允许继续加载。文件搜索的扫描预算是资源边界，截断必须对用户可见。会话历史的旧消息与实时消息合并时按标识去重。旧接口兼容会保留部分完整列表读取路径，新页面和新增调用方须显式请求分页。此决定无需数据库迁移。

## 验证

API Key、任务、文件搜索、选人、会话、技能发布、评估、反馈和技能目录分别由后端分页与授权测试及前端换页测试验证。涉及 PostgreSQL 授权查询与接口返回契约的行为，还须在真实 PostgreSQL 和 HTTP 环境验证；页面交互须在真实浏览器验证。仓库的工程契约检查、单元测试、前端静态检查与构建用于提交门禁。
