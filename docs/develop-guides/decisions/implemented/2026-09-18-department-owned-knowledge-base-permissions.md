# 知识库采用部门归属与继承管理权限

状态：implemented
类型：feature
Owner：backend/package/yuxi/permissions/resource_permission.py

## 问题

知识库目前以 `created_by` 作为资源所有者，创建人天然获得管理权限。这与部门知识库的业务语义不一致：创建人调岗或离职后不应改变知识库管理边界，所属部门管理员应当天然拥有管理权限，超级管理员应当拥有全局管理权限。同时现有数据库没有知识库所属部门字段，若增加列会引入结构迁移。

## 决策

- 知识库由部门持有，`created_by` 仅用于审计，不参与知识库授权。
- 超级管理员对全部知识库继承 `MANAGE`；知识库所属部门的部门管理员继承 `MANAGE`。
- 显式共享范围继续授予 `READ`、`EDIT`、`MANAGE`，普通用户的角色上限保持为 `EDIT`。
- 只有超级管理员和部门管理员可以创建知识库；部门管理员只能选择本部门，超级管理员可以选择任意有效部门。
- 不新增数据库列，将 `owner_department_id` 写入知识库现有 `share_config` JSON。更新共享配置时由服务端保留该字段，客户端不能借此转移归属。
- 对没有 `owner_department_id` 的历史知识库，读取时根据 `created_by` 对应用户当前部门提供兼容归属；后续保存共享配置时固定该部门。
- 前端展示系统继承管理人，并从“指定协管成员”候选中排除超级管理员和所属部门管理员，避免重复配置。
- Agent 与 Skill 继续保留创建人资源所有权，不受本决策影响。

## 后果

- 创建人只作为审计信息展示；仅凭 `created_by` 不再获得知识库读取、编辑或管理权限。
- 知识库所属部门管理员与超级管理员无需出现在显式共享名单中，也无法在“指定协管成员”里被重复配置。
- 新建知识库不需要数据库结构迁移；归属信息保存在现有 `share_config` 中，并由后端在更新时强制保留。
- 历史知识库读取时兼容按创建人部门解析，后续保存后即固化部门归属。

## 替代方案

- 新增 `owner_department_id` 数据库列：约束更强、查询更直接，但需要数据库结构迁移与历史数据回填，本阶段不采用。
- 继续用创建人作为管理权来源：无需改动，但无法表达部门归属，也会让人员变动影响管理边界，不采用。
- 将部门管理员显式写入 `manage_scope`：会产生冗余配置，管理员变更后还需批量更新所有知识库，不采用。

## 风险

- 历史知识库没有固定归属时，兼容归属取创建人的当前部门；在首次保存配置前，创建人调岗会改变兼容归属。新建和再次保存后的知识库不受此影响。
- 所属部门被删除时，现有部门删除流程需要继续保证用户迁移与知识库归属语义可解释；本阶段不额外引入级联迁移。
