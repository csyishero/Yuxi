# 技能市场下架与上架范围调整设计

日期：2026-10-20；状态：待书面确认

## 目标与边界

管理员能够撤下已发布的市场 Skill；超级管理员能够直接在部门市场与全公司市场之间调整已上架条目的当前可见范围。下架、范围收窄都必须阻止受影响成员在后续 Agent 任务中使用已有市场安装，同时保留安装记录、不可变审核版本和历史申请。范围重新覆盖某成员时，未经历下架的旧安装恢复可用；经历下架的安装必须由本人确认新审核版本才恢复。

内容编辑、直接改写审核快照、自动升级旧安装、强制终止正在执行的 Agent 任务不在本次范围内。内容变化沿用作者重新提交、管理员审核、生成新版本的现有流程。下架也不释放市场 slug，避免旧安装、历史记录或共享 Skill 发生身份冲突。

本设计以现有 `MarketSkill` 稳定条目、`MarketSkillRelease` 不可变版本、`MarketSkillInstall` 用户安装指针和市场审核申请为基础。直接共享 Skill 的启停与授权保持独立。

## 条目与安装状态

市场条目保留最新审核版本指针，并增加独立的当前上架状态。下架不清空版本指针，也不删除已发布目录。条目另保存上架批次和本批次可用于新任务的最早版本：现有条目迁移后视为已上架的首批次；每次下架使批次前进；再次审核通过时，新版本成为该批次的起始版本。

安装记录保存用户最后一次主动确认的上架批次。首次安装或手动升级确认当前批次；下架后，旧安装记录的批次落后于条目，运行时始终拒绝它。再次上架只开放新的审核版本，不自动改变旧安装。用户在当前范围内点击“确认升级”后，安装指针改为新版本并确认当前批次。普通安装接口已有安装行时直接返回的行为不得充当重新确认。

Agent 的技能解析和用户技能文件投影都同时检查：条目已上架、成员属于当前范围、安装已确认当前批次、版本属于当前批次。投影只提供当前批次内且不高于用户已安装版本的文件；旧批次版本仍存于发布存储和审核历史，不会在重新上架后回到新任务的技能目录。下架及范围收窄时，服务端先锁定所有安装者及持有旧投影的用户，再撤去相关版本投影；这些锁与 Agent 运行时投影刷新使用同一组按用户划分的事务锁，并持续到市场状态提交。并发刷新的调用要么先完成、随后被撤销，要么在提交后读取新状态，因此不能把旧文件重新投影到新任务。无安装记录的新用户不会获得该条目的市场投影。撤销失败则拒绝这次状态变更，不把未同步的策略报告为成功；现有执行不主动取消，但撤销后的文件访问不保证继续成功。

例如，成员在首批次安装 v2，条目当前已发布 v3。下架后批次前进，v2 安装不可用；作者提交新快照并获批为 v4 时，v2 安装仍不可用。成员主动确认升级到 v4 后，新任务只获得本批次的版本目录。单纯把条目从全公司改到某部门不改变批次，因此后来重新进入可见范围的旧安装无须重复确认。

## 操作与权限

| 操作 | 部门管理员 | 超级管理员 | 作者／普通成员 |
| --- | --- | --- | --- |
| 查看管理清单 | 记录的市场范围为本部门的条目，含已下架 | 全部条目 | 无权限 |
| 下架 | 已上架且当前范围为本部门的条目 | 全部已上架条目 | 无权限 |
| 调整当前上架范围 | 无权限 | 部门与全公司之间、部门之间 | 无权限 |
| 审核再次上架 | 按现有审核权限；跨作者部门的条目不可批准 | 按现有审核权限 | 作者重新提交快照 |

部门管理员权限跟随条目的当前市场范围，不跟随作者所属部门：全公司条目即使由本部门作者创建，也只能由超级管理员下架；条目被超级管理员移到另一部门后，仅目标部门管理员和超级管理员可下架。下架只作用于已上架条目。它在同一业务事务中更新条目状态和批次、留下操作者、时间及原状态的操作日志，并将该作者／原件在下架前已经待审的市场申请标为“已驳回”，说明“条目已下架，需重新提交”。作者需从仍存在的个人原件重新提交快照；新申请获批后沿用原市场条目、slug 和递增版本。跨作者部门的既有条目由超级管理员审核新版，包括超级管理员把条目移动到其他部门的情形。

范围调整只作用于已上架条目，不改变上架批次、已安装版本或任何历史审核申请的 `read_scope`、`department_ids`。全公司转部门或转入其他部门时，超级管理员必须明确选择有效目标部门；转全公司时清除当前部门绑定。服务端按依赖的授权配置验证其可用范围完整覆盖目标受众：全公司市场要求每项依赖面向全公司，部门市场要求覆盖该部门；仅给部分成员的单独授权不足以通过。工具还须存在，MCP 与共享 Skill 还须启用并可调用。验证不能只按超级管理员自己或抽样成员的权限判断。验证失败时原范围保持不变并给出依赖原因。范围收窄让范围外旧安装暂不可用且仍可卸载；再次扩大到该成员时，未经历下架的旧安装自动恢复。

同一既有条目的市场快照提交、下架、范围修改、再次审批和安装确认按数据库条目锁串行化，统一按“条目、申请、用户投影 UID”的顺序取锁，UID 按固定顺序处理。提交在锁内复制个人原件并记录当时的上架批次；审批仅接受同批次申请。下架使批次前进并驳回旧待审申请。这样，在下架前取得锁的提交会先落库再失效；在下架后取得锁的提交才是可用于再次上架的新快照。管理操作携带页面读取到的原状态，状态已变化时返回冲突并要求刷新，避免过期页面覆盖新决定。状态变更与操作日志共用事务；如果投影撤销失败，不提交会扩大实际使用权的策略变更。

## HTTP 与页面

现有市场目录、搜索、详情、排行榜、文件预览、安装、升级和点赞只接受当前已上架且对调用者可见的条目；下架或范围外条目对普通成员表现为不存在。已安装摘要接口继续允许本人读取，且在不可用时只返回稳定 slug、已安装版本、不可用原因与卸载入口所需字段，不泄露当前发布内容、作者信息或目标部门。卸载保持可用。

新增仅管理员可读的 `GET /api/skill-market/-/management` 与对应管理详情，覆盖权限内已上架和已下架条目。`POST /api/skill-market/{slug}/unpublish` 执行下架；`PUT /api/skill-market/{slug}/scope` 仅供超级管理员调整范围，部门范围必须包含目标部门 ID。两个写请求都携带操作者在页面看到的原状态，后端锁定条目后比较，变化时返回冲突。管理入口与普通市场目录分开，确保下架条目在管理端可查而不进入成员目录。非法范围、目标部门或依赖返回明确错误；无权限、过期状态和条目不可见分别按授权／冲突／不可见处理。

技能市场详情在有权管理员视角展示“调整范围”“下架”。管理清单显示已下架状态与再上架所需的“作者重新提交、等待审核”路径。作者的“发布与审核记录”分别显示当次审核范围和当前条目状态／范围；下架后保留历次申请及快照，不能仅凭最新版本存在就显示“已上架”。普通成员的市场目录不展示下架或范围外条目；“我的技能”仅为本人旧安装显示安全摘要、原因和卸载。重新上架且成员属于当前范围时，旧安装显示“需确认新版”，点击确认升级后才重新可用。页面不增加独立的“Agent 新任务可选技能”面板，运行侧约束由服务端执行。

## 迁移与验证

业务 Schema 从现有 v14 增量升级，幂等补齐条目上架状态／批次／本批次起始版本、安装确认批次及市场申请所属批次。现有已发布条目和安装记录视为首批次有效，现有不可变版本、申请历史与用户安装版本不改写。迁移失败不得记录新版本号；再次运行可安全收敛。

## 具体验收用例

用例以部门甲、部门乙、两部门成员与管理员、超级管理员及一个已有 v3 的市场条目为基本数据；需要验证旧安装时，成员预先安装 v2。所有拒绝用例都核对数据库状态和用户技能目录没有意外变化，不能只断言错误消息或 HTTP 状态码。

| 场景 | 操作 | 必须观察到的结果 | 证据层 |
| --- | --- | --- | --- |
| 本部门下架 | 甲部门管理员下架当前范围为甲部门的条目 | 市场目录立即消失；状态与批次更新；版本、安装行保留；操作日志记录操作者和原状态 | 真实 HTTP＋PostgreSQL |
| 越权或重复下架 | 普通成员、作者或乙部门管理员尝试下架甲部门条目；甲部门管理员尝试下架全公司条目；重复下架已下架条目 | 请求被拒绝；状态、批次、日志、安装和文件投影保持原状态 | 真实 HTTP＋PostgreSQL＋文件 |
| 下架阻断所有入口 | 成员保留旧安装后访问目录、详情、排行、文件、安装、升级、点赞及新 Agent 任务 | 公共入口不可访问；新任务不解析该 Skill；旧安装摘要只含安全字段，仍可卸载 | 真实 HTTP＋运行时＋文件 |
| 已运行任务 | Agent 任务已经开始后管理员下架其市场 Skill | 系统不主动把该 Run 标为取消；下架后的新任务均不再得到该 Skill | 真实 Run 状态＋后续运行时 |
| 待审申请失效 | 作者在下架前提交待审快照，然后管理员下架并尝试批准该申请 | 旧申请标为已驳回并注明下架原因；批准不能生成版本 | 真实 HTTP＋PostgreSQL |
| 重新上架 | 作者下架后重新提交快照并获有权管理员批准 | 沿用原条目与 slug；新版本为 v4；历史 v1～v3 和历次申请不被改写 | 真实 HTTP＋PostgreSQL＋发布目录 |
| 旧安装重新确认 | v2 安装用户在 v4 再上架后分别调用普通安装和确认升级 | 普通安装不能解除暂停；升级确认后安装指向 v4、批次更新，新任务才可用 | 真实 HTTP＋PostgreSQL＋运行时 |
| 旧批次文件隔离 | 上述用户确认 v4 并启动新 Agent 任务 | 投影仅包含当前批次允许的版本，v1～v3 文件不重新出现 | 真实用户投影目录＋运行时 |
| 范围收窄与恢复 | 超级管理员把全公司条目改为甲部门，再改回全公司，期间不下架 | 乙成员的公共目录先隐藏该条目，但旧安装安全摘要仍可读；范围恢复后旧安装自动可用，版本、批次、发布内容和审核历史不变 | 真实 HTTP＋PostgreSQL＋文件 |
| 越权或无效状态改范围 | 部门管理员、作者、普通成员调用范围接口，或超级管理员修改已下架条目 | 请求被拒绝；当前范围、批次、日志和用户投影不变 | 真实 HTTP＋PostgreSQL＋文件 |
| 部门转移 | 超级管理员把甲部门条目移到乙部门 | 甲管理员失去管理权，乙管理员可下架；甲成员旧安装保留且不可用；乙成员可见条目 | 真实 HTTP＋PostgreSQL |
| 跨部门续版审核 | 甲部门作者的条目由超级管理员移到乙部门后再次提交快照 | 乙部门管理员不能批准新版本；超级管理员可以批准，版本沿用乙部门范围 | 真实 HTTP＋PostgreSQL |
| 无效目标与依赖 | 目标部门不存在；依赖只授权部分目标成员、缺失、停用或不可调用；分别尝试部门与全公司范围 | 修改被拒绝且说明原因；原范围、批次与文件投影不变 | 真实 HTTP＋PostgreSQL＋文件 |
| 管理清单授权 | 甲、乙部门管理员、超级管理员和普通成员读取管理列表与详情，其中包含已下架条目 | 部门管理员仅见记录范围为本部门的条目，超级管理员见全部，普通成员不能读取；公共目录仍隐藏已下架条目 | 真实 HTTP＋PostgreSQL |
| 过期管理页面 | 两名管理员读取同一原状态，第一人修改后第二人提交旧状态 | 第二次返回冲突；第一人的决定未被覆盖 | 真实 HTTP＋PostgreSQL |
| 提交与下架交错 | 控制提交快照与下架的取锁顺序，分别让提交先完成和下架先完成 | 前者申请被下架失效，后者申请记录新批次；旧批次申请在任何顺序都无法再次上架 | PostgreSQL 并发集成 |
| 安装确认与下架交错 | 控制升级确认和下架的取锁顺序，分别让确认先完成和下架先完成 | 两种顺序都不能让旧安装在下架后保持有效批次 | PostgreSQL 并发集成 |
| 投影刷新与撤销交错 | 控制 Agent 投影刷新与下架或范围收窄的取锁顺序，并在撤销部分用户后注入失败 | 成功后受影响用户目录均无旧版本；失败时状态、范围、批次和操作日志不变 | PostgreSQL＋真实文件并发集成 |
| 存量迁移 | 从 v14 库升级并重复执行迁移 | 原有条目、安装在首批次仍可用；新列正确回填；版本记录只在成功后前进，重复运行无副作用 | 真实 PostgreSQL 迁移 |
| 页面状态 | 分别以管理员、作者、范围外旧安装成员打开技能页，并完成下架、改范围、再上架 | 管理清单保留已下架条目；作者看到审核时与当前范围；范围外成员仅见安全摘要；再上架后有确认升级入口 | 前端单测＋真实页面 |

关键拒绝路径先写能在旧实现下失败的测试，再实现行为。通过 HTTP 状态码后还须回读数据库和真实用户目录；前端单测之外运行 lint、构建和真实页面检查。文档与迁移检查按仓库工程规范执行，并由独立 Reviewer 对照本设计审查完整 diff 和证据。
